# 프론트엔드 화면 전환과 성능 개선 계획

## 목적과 실행 범위

기존 화면과 데이터 의미를 유지하면서 화면 전환의 불필요한 대기, 중복 요청과 반복 계산을
줄이는 구현 계획이다. 구현은 별도 작업 요청 뒤 시작하며, 현재 구현 상태는
[구현 정보](implementation.md)가 정본이다.

수정 대상은 이 Repository의 프론트엔드 코드, 테스트와 관련 문서다. 검증에는 로컬의
격리된 컨테이너와 Scrap 서버의 대시보드 개발 컴포넌트를 사용한다. Backend, Camera Media
Service와 Edge Platform의 코드, 설정과 저장 데이터는 변경하지 않는다.

화면 유지 조건은 [프로젝트 명세](project-spec.md#사용자-기능), 데이터 의미와 인증 및
영상 경계는 [외부 연동 계약](contracts/README.md)을 따른다. 원격 반영, Issue와
Pull Request (PR) 생성 및 Release는 별도 명시적 요청 범위다.

## 유지 조건

유지 대상은 카드 배치, 기존 기능, 인증과 데이터 의미의 4개 영역이다.

| 영역 | 유지 조건 |
| --- | --- |
| 화면 배치 | 카드 위치와 크기, 표와 글꼴, 헤더 및 푸터 높이, 빈 결과에서도 같은 기본 영역 |
| 기존 기능 | 기간 및 유형 조회, 알림 읽음 처리, 관리자 설정, 영상 확대와 녹화 다운로드 |
| 인증 | Backend session과 역할 확인, session 만료 및 권한 오류 처리, 기존 요청 보호 |
| 데이터 의미 | 서버 시각과 대상 식별자, 유효성 및 결측값, 확보 및 누락 구간, 최신 단건 확인 |

실제 화면 전환 대기 중에는 메뉴, 사용자 도구와 수신 상태 문구의 기존 숨김 규칙을
유지한다. 준비가 끝나면 확인한 권한에 맞는 메뉴를 한 번에 표시한다. 추가 안내 문단이나
카드 크기 변경으로 로딩과 오류를 표현하지 않는다.

## 목표 구조

데이터와 화면의 수명은 4개 영역으로 분리한다.

| 영역 | 책임 | 수명과 갱신 기준 |
| --- | --- | --- |
| 앱 공통 상태 | runtime 설정, session, 대상 식별자와 공통 헤더 | 최초 앱 진입, 필요한 인증 재확인, 로그아웃과 계정 변경 |
| 공통 수신 상태 | monitoring snapshot, 수신 상태와 알림 | 인증된 앱의 단일 실시간 구독과 독립적인 알림 조회 |
| 화면별 조회 | 현황 부가 정보, 이력, 녹화 목록과 관리자 정보 | 해당 화면과 조회 조건에 따른 요청 및 취소 |
| 화면별 자원 | 영상 player, 녹화 단건 갱신, timer와 modal | 화면 진입과 선택, 종료 및 인증 변경에 따른 정리 |

React, TypeScript와 Vite를 유지한다. 추가 의존성은 구현 전에 필요성, 빌드 크기와
검증 영향을 검토하고 [개발 절차](development-workflow.md#실행-범위)에 따라 보고한다.

## 실행 단계와 예상 시간

작업은 5단계이며 앞 단계의 완료 조건을 확인한 뒤 다음 단계로 진행한다. 예상 시간은
구현, 회귀 검증, 실제 서버 확인과 리뷰를 포함해 약 8~14시간이며, 작업 일정은
1~2작업일을 기준으로 한다. 검증 환경에 접근할 수 있고 외부 계약이 유지된다는 전제이며,
인증 및 연결 수명의 회귀 문제에 따른 추가 수정 시간은 별도다.

| 단계 | 작업 | 완료 조건 | 예상 시간 |
| --- | --- | --- | --- |
| 1. 기준선 측정 | production build의 최초 접속, 반복 전환과 요청 흐름 측정 | 네트워크 대기, 화면 준비와 영상 준비 시간의 구분 | 0.5~1시간 |
| 2. 조회와 로딩 분리 | 공통 초기화, 화면별 필수 조회와 알림 및 부가 조회 분리 | 준비된 본문이 관계없는 응답을 기다리지 않는 구조 | 2~3시간 |
| 3. 앱 내부 화면 전환 | client-side routing과 공통 상태 수명 적용 | 전체 페이지 재로드 없는 메뉴 이동과 기존 URL 동작 유지 | 2~3시간 |
| 4. 갱신과 자원 정리 | 요청 중복 방지, 제한된 메모리 캐시와 구독 및 player 수명 정리 | 중복 연결과 이전 화면의 불필요한 작업 방지 | 1.5~2.5시간 |
| 5. 검증과 리뷰 | 기능, 배치, 오류 복구와 장시간 반복 조작 검사 및 보정 | 회귀 검사 통과와 동일 조건의 성능 비교 | 2~4시간 |

### 1단계 기준선 측정

측정 기준은 production build와 동일한 브라우저, 서버, 네트워크 및 계정 역할이다.
Vite 개발 서버와 소스 자동 동기화 환경의 결과는 production 결과와 구분한다.

수집 항목은 다음과 같다.

- 최초 접속과 이미 방문한 화면의 재진입 시간
- 메뉴 선택부터 기본 카드 표시와 필수 데이터 표시까지의 시간
- 요청 수, 응답 body 완료 시각과 중복 요청
- JavaScript 처리 시간, main thread의 long task와 변경 영역의 렌더링 횟수
- 실시간 구독 수, 영상 연결 수와 반복 전환 후 메모리 사용 추이

화면 표시, 영상 첫 frame과 MP4 파일 준비는 각각 별도로 측정한다. 기존 테스트 실패는
기준선에서 식별하며 새 변경의 회귀와 구분한다.

### 2단계 조회와 로딩 분리

주요 대상은 `src/data/dashboard-data-source.ts`, `http-dashboard-data-source.ts`,
`use-dashboard-data.ts`와 화면별 데이터 연결이다. Synthetic data source에도 같은 경계를
적용해 실제 API (Application Programming Interface) 모드와 같은 수명 관리로 검증한다.

1. 인증 및 설정 확인과 화면별 조회의 책임을 분리한다.
2. 서버 시각이나 식별자가 필요한 요청 순서는 유지하고 독립적인 조회만 병렬 실행한다.
3. 알림과 현황 부가 정보의 지연이 준비된 본문을 막지 않도록 로딩 및 오류 상태를 분리한다.
4. 인증된 기본 카드 영역을 유지하며 각 영역의 준비, 빈 결과, 실패와 이전 결과를 구분한다.
5. Server-Sent Events (SSE) snapshot 갱신에 변경하지 않은 이력과 녹화 metadata를 매번 복제하지 않도록 데이터 전달 경계를 정리한다.

알림 응답만 4초 지연시킨 격리 테스트에서, 인증과 해당 화면의 필수 데이터가 준비되면
본문을 표시하는 것이 완료 조건이다. 늦은 응답이나 실패는 알림 영역에서 처리하며
빈 알림 또는 정상 수신으로 오인하지 않는다.

### 3단계 앱 내부 화면 전환

주요 대상은 `src/App.tsx`, `src/app-routing.ts`, `src/RuntimeConfiguredApp.tsx`,
`src/components/DashboardShell.tsx`와 화면별 진입 경계다.

1. 같은 앱의 일반 메뉴 이동에 client-side routing을 적용한다.
2. URL (Uniform Resource Locator)의 경로와 기존 query parameter, 뒤로 및 앞으로 이동을 유지한다.
3. 직접 URL 접속, 브라우저 새로고침, 새 탭과 보조키를 사용하는 링크 동작을 유지한다.
4. 단순 메뉴 이동만으로 runtime 설정, 공통 session 상태와 실시간 구독을 재생성하지 않는다.
5. 관리자 진입과 인증 오류 등 필요한 권한 재확인을 유지한다.
6. 이전 화면의 modal, focus와 스크롤을 정리하고 새 화면의 키보드 진입을 검증한다.

runtime 설정은 전체 페이지 로드 시 확인하는 기존 적용 경계를 유지한다. 설정 변경을
즉시 반영하는 별도 기능은 추가하지 않는다. 화면 모듈은 필요한 시점에 로드하며 모든
화면과 영상 구현을 초기 JavaScript에 포함하지 않는다.

### 4단계 갱신과 자원 정리

주요 대상은 화면별 조회 hook, Hypertext Transfer Protocol (HTTP) adapter의 구독 경계와
기존 영상 및 녹화 컴포넌트다.

1. 같은 계정, 대상과 조회 조건의 진행 중 읽기 요청을 중복 실행하지 않도록 조정한다.
2. 필요한 조회 결과만 크기와 유효 기간이 제한된 메모리에 보관한다.
3. 캐시 키에 계정, pit 및 camera, 녹화 source와 조회 조건을 반영한다.
4. 설정 저장과 알림 읽음 처리 후 관련 결과를 갱신하고 로그아웃 및 계정 변경 시 캐시를 제거한다.
5. SSE는 인증된 앱에서 하나만 유지하고 현황 전용 조회는 현황 화면의 수명에 맞춰 실행한다.
6. 화면 이탈과 선택 변경 시 요청, timer, player와 Blob URL을 정리하고 늦은 응답을 무시한다.
7. 측정으로 확인한 반복 계산과 불필요한 렌더링만 줄인다.

캐시는 Backend의 접근 제어와 최신 녹화 단건 확인을 대신하지 않는다. 다운로드와 export의
권한 및 가능 여부는 해당 동작의 기존 확인 절차를 유지한다. 설정 저장, export 준비와
알림 동작 같은 변경 요청을 캐시하거나 자동으로 재전송하지 않는다. 갱신에 실패한 이전
결과를 최신 상태나 정상 값으로 표시하지 않는다.

### 5단계 검증과 리뷰

검증은 단위 및 컴포넌트, 브라우저, production 이미지와 실제 서비스의 경계로 구분한다.
설치, 검사와 컨테이너 실행 및 회수 명령은
[기존 검증 절차](development.md#개발과-검증-컨테이너)를 사용한다.

브라우저 검증의 기본 해상도는 FHD (Full High Definition) 1920 x 1080이며,
1280 x 900과 1440 x 900에서도 기존 배치를 검사한다. 실제 서비스 검증은 기존 데이터를
읽는 동작을 기본으로 하며, 관리자 저장과 테스트 알림 등 상태 변경은 격리된 fixture에서
검증한다.

| 시나리오 | 확인 조건 |
| --- | --- |
| 알림 및 부가 요청 지연과 실패 | 준비된 본문 표시, 실패 영역의 격리와 값의 의미 유지 |
| 메뉴 연속 이동과 역순 응답 | 최종 화면에 해당하는 결과만 적용, 이전 요청 취소 |
| 새로고침, 직접 접속과 브라우저 이동 | 기존 경로, query parameter와 권한 동작 유지 |
| 로그인, 로그아웃과 역할 변경 | 계정 간 데이터 격리, 권한 확인 전 정보 미노출 |
| HTTP 401 및 403, session.expired | 기존 계약에 따른 접근 제한과 요청 및 연결 정리 |
| 이력 및 녹화 조회, 영상 확대와 다운로드 | 필터, 재생 위치, 단건 확인과 파일 준비 흐름 유지 |
| 관리자 저장과 알림 읽음 처리 | 성공 및 실패 처리, 관련 캐시 갱신과 중복 전송 방지 |
| 긴 녹화 범위와 대량 이력 | 입력 규모에 따른 처리 시간과 표시 요소 수의 관리 |
| 최소 30분 반복 조작 | 구독 및 영상 연결 중복과 지속적인 메모리 증가 부재 |

리뷰 도구와 결과 처리 기준은 [검증 기준](testing.md#변경-검증과-리뷰)을 따른다.
이 작업의 리뷰는 데이터 격리, 인증, 요청 순서, 캐시 무효화와 자원 정리를 우선 검토한다.

## 최종 완료 조건

- 관련 정적 검사, 타입 검사와 전체 회귀 테스트 통과
- production 이미지 및 실제 서비스 연동 검증 통과
- 기존 빌드 용량 제한 유지
- 동일 조건의 변경 전후 화면 표시 시간, 요청 수와 연결 수 비교
- 기존 카드 배치, 로딩 표시 규칙과 기능의 유지
- 리뷰 지적 해소와 수정 후 재검증
- 채택한 구현과 재현 방법의 구현 정보 반영

Backend 응답, 네트워크 전송과 Media Service의 영상 및 export 준비 시간은 이 작업으로
단축을 보장하지 않는다. 완료 판단은 불필요한 대기와 반복 작업의 제거 및 측정 결과를
기준으로 하며 모든 화면의 데이터를 일정 시간 안에 받는다는 목표를 두지 않는다.
