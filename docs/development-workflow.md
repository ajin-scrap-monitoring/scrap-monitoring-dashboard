# 프론트엔드 개발 워크플로우

## 문서 역할

이 문서는 요구사항에서 배포 검증까지 이어지는 프론트엔드 개발 순서와
각 단계의 완료 조건을 정의한다. 프로젝트 목적과 범위는
`docs/project-spec.md`, 미확정 설계안은 `docs/design-reference.md`, 실제로
채택한 기술과 구현 구조는 `docs/implementation.md`에서 관리한다.

## 현재 프로젝트의 제약

- 프론트엔드는 서버가 제공하는 측정, 상태, 이력과 예측 결과를 표현하는 책임
- 측정선별 결과와 통합 결과의 관계, 표시 지표의 개수와 판정 의미가
  확정되지 않은 상태
- 상태 데이터, 실시간 갱신, 실시간 영상, 녹화 영상과 인증의 외부
  계약이 필요한 상태
- 로딩, 데이터 없음, 오류, 연결 끊김과 측정 불가를 서로 구분해야
  하는 관리자용 화면
- 실제 장비와 네트워크 흐름 확인이 우선이며 측정 로직 시뮬레이션은
  프론트엔드 범위에서 제외된 상태

## 전체 단계

워크플로우는 8단계다.

1. 프로젝트 계약 확정
2. 요구사항과 사용자 흐름 정의
3. UI (User Interface) 설계와 디자인 시스템 정의
4. 구현 기준선 결정
5. 컴포넌트 구현과 독립 검증
6. 화면 통합과 상태 전이 검증
7. 외부 서비스와 사용자 흐름 검증
8. 빌드, 배포 산출물과 운영 검증

앞 단계의 산출물이 뒤 단계의 입력이 된다. 구현 중 계약이나 사용자 흐름이
바뀌면 해당 정본을 먼저 갱신하고 영향을 받는 디자인, 개발 대역 데이터,
코드와
테스트를 함께 갱신한다.

## 1. 프로젝트 계약 확정

Figma에서 화면을 고정하기 전에 다음 계약을 확인한다.

- 관리 단위와 측정선별 결과, 통합 결과의 관계
- 데이터 개체, 필드, 단위, 시간대, 결측과 오류 형식
- 상태 갱신 방식과 재연결 후 동기화 규칙
- 실시간 및 녹화 영상의 제공 방식과 재생 제약
- 조회와 관리 기능의 인증, 권한과 세션 규칙
- 대상 브라우저, 해상도, 입력 방식과 네트워크 조건
- 정적 파일 제공 위치, 기본 경로, 실행 시점 설정과 캐시 정책

완료 조건은 확정된 항목과 미확정 항목, 각 미확정 항목의 결정 주체가
구분된 상태다.

## 2. 요구사항과 사용자 흐름 정의

설계 담당자는 요구사항을 분해하고 미확정 사항을 발견하며 인수 조건 초안을
작성한다. FigJam은 사용자 작업, 화면 이동, 정상 경로와 오류 및 복구 경로를
표현한다.

사용자 흐름에는 현황 확인, 이력 탐색, 녹화 영상 재생과 관리자 설정
변경을 포함한다. 각 흐름은 정상, 로딩, 데이터 없음, 오류, 연결 끊김,
권한 없음과 세션 만료 상태를 필요한 범위에서 구분한다.

완료 조건은 주요 사용자 흐름과 각 흐름의 관찰 가능한 인수 조건이 연결되고
프로젝트 담당자가 승인한 상태다.

## 3. UI 설계와 디자인 시스템 정의

Figma는 확정된 사용자 흐름과 외부 계약을 기준으로 화면, 반응형 규칙,
컴포넌트와 상태를 설계한다. 디자인 토큰은 색상, 글꼴, 간격, 크기,
모서리와 그림자 같은 반복 값에 의미 있는 이름을 부여한 것이다.

설계 산출물에는 다음 내용을 포함한다.

- 화면별 정상과 비정상 상태
- 컴포넌트 변형, 상호작용과 콘텐츠 규칙
- 디자인 토큰과 Figma 변수
- 키보드, 포커스, 대비, 레이블과 오류 안내를 포함한 접근성 조건
- 확정된 브라우저 크기별 배치 규칙
- 코드에서 재사용할 자산과 파일 제공 조건

완료 조건은 구현 대상 프레임과 컴포넌트가 이름, 상태, 변형과 토큰
수준에서 식별 가능하고 프로젝트 담당자가 구현 기준으로 승인한 상태다.

## 4. 구현 기준선 결정

제품 코드를 작성하기 전에 다음 8개 기술 기준을 결정한다.

1. Node.js 실행 위치, 설치, 버전 고정과 갱신 정책
2. 패키지 관리자, 버전 고정과 lock file 정책
3. 직접 의존성과 라이선스 정책
4. 대상 브라우저, 빌드 출력 호환성과 브라우저 Web API (Application Programming
   Interface) 지원 정책
5. 애플리케이션 구조와 외부 연동 경계
6. 개발 서버와 프로덕션 빌드 방식
7. 단위, 컴포넌트, 화면과 End-to-End (E2E) 테스트 범위
8. 정적 산출물의 패키지 형식과 배포 Repository 인계 계약

Node.js 버전은 대상 브라우저가 아니라 빌드 도구의 요구 버전과 지원
주기를 기준으로 선택한다. 브라우저 호환성은 빌드 출력 대상, Cascading
Style Sheets (CSS), Web API 사용 범위와 브라우저 검증으로 별도 관리한다.

패키지는 요구사항에서 확인된 필요와 버전, 라이선스, 유지보수성,
브라우저 지원 범위를 확인한 뒤 추가한다. 빌드 도구와 산출물은 배포
방식과 실행 시점 설정 방식을 확인한 뒤 확정한다.

완료 조건은 확정된 선택과 근거가 `docs/implementation.md`에 기록되고, 빈
애플리케이션을 같은 방법으로 재현 가능하게 설치, 검사, 테스트와 빌드할
수 있는 상태다.

## 5. 컴포넌트 구현과 독립 검증

컴포넌트 단위로 다음 작업을 반복한다.

1. 구현할 Figma 프레임 또는 컴포넌트와 인수 조건 선택
2. 구현 작업자가 Figma MCP (Model Context Protocol)로 레이아웃, 변수,
   컴포넌트와 자산 컨텍스트 확인
3. 구현 작업자가 저장소의 구조, 스타일 규칙과 외부 계약에 맞는 React 코드 구현
4. Storybook 스토리로 정상, 경계, 로딩, 데이터 없음과 오류 상태 표현
5. 렌더링, 상호작용, 접근성과 필요한 시각 회귀 검증
6. 구현 결과와 인수 조건을 기준으로 코드 또는 Figma 설계 보정

Figma MCP는 Figma의 설계 컨텍스트를 구현 작업자에게 전달하는 경계다. MCP가 반환한
내용을 배포 가능한 코드로 간주하지 않고, 저장소 규칙과 검증 결과를 적용해
구현한다. Code Connect는 재사용할 코드 컴포넌트가 생긴 뒤 Figma
컴포넌트와의 매핑이 필요할 때 적용한다.

Storybook은 React 구현이 모두 끝난 뒤 한 번 실행하는 단계가 아니다. 컴포넌트
구현과 스토리 작성, 검증을 하나의 반복 단위로 취급한다.

## 6. 화면 통합과 상태 전이 검증

검증된 컴포넌트를 화면과 경로로 조립한다. 외부 서비스 대신 확정된 계약을
따르는 통제 가능한 합성 데이터와 시험 영상을 사용한다. 시간 흐름, 상태
변경, 재연결, 인증 만료와 설정 변경 충돌을 화면 수준에서 검증한다.

완료 조건은 주요 사용자 흐름을 외부 서비스 없이 재현하고 인수 조건을
확인할 수 있는 상태다.

## 7. 외부 서비스와 사용자 흐름 검증

Playwright는 브라우저에서 사용자가 보고 조작하는 행동을 기준으로 주요 E2E
흐름을 검증한다. 먼저 통제 가능한 테스트 데이터와 네트워크 응답을 사용해
재현성을 확보한다. 다음으로 통합 환경에서 실제 API (Application Programming
Interface), 실시간 갱신, 인증, 실시간 영상과 녹화 영상을 검증한다.

Playwright는 측정 값 산출 알고리즘의 정확성을 검증하지 않는다. 서버가 제공한
결과와 상태를 브라우저가 계약대로 표시하고 사용자 요청을 전송하는지
검증한다.

## 8. 빌드, 배포 산출물과 운영 검증

로컬에서 재현 가능한 검사, 타입 검사, 테스트와 빌드 명령을 Continuous
Integration (CI)에 적용한다. CI 통과 후 프로덕션 빌드를 하나의 배포
산출물로 패키징하고 동일한 산출물을 검증과 배포에 사용한다.

이 Repository의 산출물 검증에는 다음 내용을 포함한다.

- 대상 브라우저의 정적 파일 로드와 기본 경로
- 실행 시점 설정과 자격 증명 분리
- 배포 중 캐시된 HTML과 새 JavaScript 자산의 버전 불일치 방지
- 라이선스 고지, 소스 맵과 보안 정책
- 버전 식별, 무결성 확인과 오류 진단 정보

배포 Repository는 인계받은 정적 산출물을 사용해 Nginx, TLS,
API, 실시간 갱신, 미디어 서비스, 건강 확인과 롤백을 검증한다.

GitHub Actions 워크플로우는 이 단계의 명령과 산출물이 확정된 뒤 자동화
수단으로 구성한다.

## 도구 역할 경계

Repository에는 구현에 필요한 확정 결과만 기록한다. 제품 요구사항과 외부 경계는
`docs/project-spec.md`, 채택한 기술과 구현 결정은 `docs/implementation.md`에 기록한다.
FigJam과 Figma의 상세 작업 내용은 각 도구에서 관리하며, 구현에 필요한 외부 자산은
`docs/implementation.md`에서 식별할 수 있게 연결한다.

| 역할 또는 도구 | 역할 | 지속 기록 |
| --- | --- | --- |
| 설계 담당 | 요구사항 분해, 미확정 사항 발견과 초안 작성 | 확정한 제품 요구사항을 프로젝트 명세에 기록 |
| FigJam | 사용자 흐름과 예외 경로 시각화 | 구현에 필요한 확정 결과를 프로젝트 명세에 반영 |
| Figma | 화면, 컴포넌트, 변수와 상태 설계 | 구현에 필요한 외부 자산 연결을 구현 문서에 기록 |
| Figma MCP | Figma 설계 컨텍스트와 구현 작업자의 연결 | 기록 대상 아님 |
| 구현 작업자 | 정보 확인, React 구현, 테스트와 문서 갱신 | 코드와 Git 문서 |
| Storybook | 컴포넌트 상태 목록, 독립 개발과 검증 | 코드와 함께 추적하는 검증 자산 |
| Playwright | 통합된 브라우저의 사용자 행동 검증 | 코드와 함께 추적하는 검증 자산 |
| GitHub Actions | 확정된 검증과 배포 절차 자동화 | 워크플로우 파일 |

## 현재 출발점

프로젝트의 목적, 범위와 외부 경계는 정의되어 있다. 측정 결과, 인증,
실시간 데이터, 미디어, 배포 환경과 대상 브라우저의 세부 계약은 미확정
상태다. Node.js, pnpm, React, TypeScript와 Vite 기준선은 채택되어 있다.
다음 기술 검토 대상은 대상 브라우저와 빌드 출력 호환성이다. 정확한 브라우저
목록은 실제 접속 단말을 확인한 뒤 확정하며 추가 제품 의존성은 필요한 기능과
지원 범위를 확인한 뒤 채택한다.

## 기술 기준 재검토 순서

기술 조사는 다음 순서를 따른다.

1. Repository 책임과 정적 산출물 인계 경계
2. Node.js 실행 위치, 설치, 버전 고정과 갱신 정책
3. 패키지 관리자, 버전 고정과 lock file 정책
4. React, TypeScript와 빌드 도구 의존성
5. 대상 브라우저, 빌드 출력 호환성과 Web API 정책
6. 라우팅, 외부 상태, 디자인 토큰, 스타일, 그래프, 시간과 입력 의존성
7. Storybook, 단위 테스트, 개발 대역 서비스와 Playwright
8. 개발 서버, 프로덕션 빌드와 실행 시점 설정
9. 정적 파일, 라이선스 고지, 소스 맵과 배포 패키지
10. 로컬 검증 명령, CI 조건과 Release 절차
