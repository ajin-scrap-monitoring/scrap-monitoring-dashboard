# 프론트엔드 개발 워크플로우

## 문서 역할

이 문서는 요구사항에서 배포 검증까지 이어지는 프론트엔드 개발 순서와
각 단계의 완료 조건을 정의한다. 프로젝트 목적과 범위는
`docs/project-spec.md`, 미확정 설계안은 `docs/design-reference.md`, 실제로
채택한 기술과 구현 구조는 `docs/implementation.md`에서 관리한다.

## 현재 프로젝트의 제약

- 프론트엔드는 서버가 제공하는 측정, 상태, 이력과 예측 결과를 표현하는 책임
- 위치별 높이 2개와 통합 대표 적재율 1개를 사용하는 화면 설계 참고안이 준비된 상태
- 상태 데이터, 실시간 갱신, 실시간 영상, 녹화 영상과 인증의 세부 외부 계약이 필요한 상태
- 로딩, 데이터 없음, 오류, 연결 끊김과 측정 불가를 구분해야 하는 관리자용 화면
- 실제 장비와 네트워크 흐름 확인이 우선이며 측정 로직 시뮬레이션은 프론트엔드 범위에서 제외된 상태

## 전체 단계

워크플로우는 8단계이며 3개 구간으로 구성한다. UI (User Interface)는 코드와
브라우저 렌더링을 기준으로 구현하고 검토한다.

| 구간 | 단계 |
| --- | --- |
| 구현 전 계약 | 1. 프로젝트 계약 확정, 2. 요구사항과 사용자 흐름 정의, 3. 구현 기준선 결정 |
| UI 구현과 검토 | 4. 코드 기반 UI 초안 구현, 5. 브라우저 검토와 반복 보정, 6. 화면 통합과 상태 전이 검증 |
| 통합과 인계 | 7. 외부 서비스와 사용자 흐름 검증, 8. 빌드, 배포 산출물과 운영 검증 |

1단계부터 3단계까지는 구현 전에 작업 입력을 확정하는 과정이다. 4단계부터
코드를 작성하며 5단계의 브라우저 검토 결과를 반영해 반복 보정한다. 한 번
확정한 프로젝트 공통 계약과 구현 기준선은 기능마다 다시 결정하지 않고,
변경이 필요한 경우에만 정본을 먼저 갱신한다.

앞 단계의 산출물이 뒤 단계의 입력이 된다. 구현 중 계약이나 사용자 흐름이
바뀌면 해당 정본을 먼저 갱신하고 영향을 받는 개발 대역 데이터, 코드와
테스트를 함께 갱신한다.

## 작업 단위 운영

개별 구현, 수정과 조사 작업은 GitHub Issue 한 개를 기준으로 관리한다. Issue는
시작 조건, 실행 범위와 완료 조건의 3단계 작업 계약이다. 작업에 해당하는 정보만
포함하며 적용할 수 없는 항목을 형식적으로 추가하지 않는다.

[Organization 공통 Issue template](https://github.com/ajin-scrap-monitoring/.github/tree/main/.github/ISSUE_TEMPLATE)의
제목과 본문 항목을 유지한다. 기능과 개선 작업은 `제안 내용`에 목적, 범위, 관찰 가능한
완료 조건, 관련 자료와 검증 방법을 작성하고 `필요한 이유`에 해결할 문제와 기대 효과를
작성한다. 오류 작업은 `오류 내용`, `재현 방법`과 `예상 동작`에 관찰 결과, 재현 조건과
복구할 동작을 작성한다. 세부 구분이 필요하면 기존 본문 항목 안에 하위 제목이나 GitHub
task list를 추가한다.

작업 계약과 진행 상태에는 GitHub 기능 5개를 사용한다.

| 기능 | 역할 |
| --- | --- |
| 공통 Issue template | 작업 입력 구조 |
| Assignee | 작업 소유자 |
| Project Status | 진행 상태 |
| Issue task list | 완료 조건과 확인 상태 |
| Pull Request (PR) 연결과 필수 검사 | 변경 추적과 병합 조건 |

### 시작 조건

작업을 시작하려면 다음 정보 중 작업 결과에 영향을 주는 항목을 Issue에서 확인할 수
있어야 한다.

- 작업 목적과 필요한 이유
- 포함 범위와 제외 범위
- 관찰 가능한 완료 조건
- 관련 정본 문서, 외부 계약, 기존 UI와 재사용 자산
- 구현하고 검증할 정상 및 비정상 상태
- 검증 방법과 대상 브라우저 크기

결과를 바꿀 수 있는 정보가 미확정이면 결정할 주체와 구현 전에 필요한 확인 내용을
Issue에 기록한다. 미확정 사항을 임의로 결정해야만 완료할 수 있는 구현은 해당 결정이
확정된 뒤 시작한다.

### 실행 범위

담당자 지정, Project 상태, 브랜치, 커밋, PR, 병합과 필수 검사는
[Organization 개발 운영 규칙](https://github.com/ajin-scrap-monitoring/.github/blob/main/GOVERNANCE.md)을
따른다.

구현 작업자는 관련 정본 문서, 기존 변경과 소스 컨텍스트를 확인하고 Issue 범위와 검증
방법을 기준으로 작업 계획을 세운다. 변경은 하나의 관찰 가능한 결과를 구현하는 데 필요한
코드, 테스트와 문서로 제한한다. 외부 계약이나 채택하지 않은 기술을 임의로 확정하지 않는다.
코딩 에이전트의 Git 변경과 외부 작업 권한은 현재 작업 요청과 Repository 작업 지침을
따른다.

기능 계약을 확인한 시점에 구현 작업자는 추가 의존성 필요 여부를 검토한다. 필요한
의존성이 있으면 설치 전에 해결할 문제, 적용 범위, 브라우저 또는 빌드 영향, 라이선스와
검증 방법을 작업 요청자에게 바로 보고한다. 채택한 의존성과 근거만
`docs/implementation.md`에 기록한다.

### 완료 조건

작업은 다음 조건 중 해당하는 항목을 모두 충족해야 완료된다.

- Issue의 관찰 가능한 완료 조건 충족
- 요구된 정상 및 비정상 상태 구현
- Issue에 정의한 검사, 타입 검사, 테스트와 빌드 통과
- 사용자 인터페이스 변경의 대상 브라우저 렌더링 확인
- 요구사항과 채택한 구현 결정의 정본 문서 반영
- [Repository 작업 지침](../.agents/AGENTS.md)의 검증과 인계 조건 충족

완료 조건의 확인 결과는 Issue task list와 PR에 반영한다. 작업 브랜치의 PR 연결,
Continuous Integration (CI), CodeQL, ruleset과 병합 뒤 상태 전이는 Organization 개발
운영 규칙을 따른다.

## 1. 프로젝트 계약 확정

화면 구현 전에 다음 계약을 확인한다.

- 관리 단위와 위치별 측정 결과, 통합 결과의 관계
- 데이터 개체, 필드, 단위, 시간대, 결측과 오류 형식
- 상태 갱신 방식과 재연결 후 동기화 규칙
- 실시간 및 녹화 영상의 제공 방식과 재생 제약
- 조회와 관리 기능의 인증, 권한과 세션 규칙
- 대상 브라우저, 뷰포트, 입력 방식과 네트워크 조건
- 정적 파일 제공 위치, 기본 경로, 실행 시점 설정과 캐시 정책

완료 조건은 확정된 항목과 미확정 항목, 각 미확정 항목의 결정 주체가
구분된 상태다.

## 2. 요구사항과 사용자 흐름 정의

작업 요청자와 구현 작업자는 요구사항을 분해하고 미확정 사항을 발견하며 관찰 가능한
인수 조건을 작성한다. 사용자 흐름과 화면 상태는 프로젝트 명세와 Issue의 텍스트, 표와
task list로 기록한다.

사용자 흐름에는 현황 확인, 이력 탐색, 녹화 영상 재생과 관리자 설정
변경을 포함한다. 각 흐름은 정상, 로딩, 데이터 없음, 오류, 연결 끊김,
권한 없음과 세션 만료 상태를 필요한 범위에서 구분한다.

완료 조건은 주요 사용자 흐름과 각 흐름의 관찰 가능한 인수 조건이 연결되고
프로젝트 담당자가 승인한 상태다.

## 3. 구현 기준선 결정

제품 코드를 작성하기 전에 다음 9개 기술 기준을 결정한다.

1. Node.js 실행 위치, 설치, 버전 고정과 갱신 정책
2. 패키지 관리자, 버전 고정과 lock file 정책
3. 직접 의존성과 라이선스 정책
4. 대상 브라우저, 빌드 출력 호환성과 브라우저 Web API (Application Programming Interface) 지원 정책
5. 애플리케이션 구조와 외부 연동 경계
6. 개발 서버와 프로덕션 빌드 방식
7. 공통 스타일, 디자인 토큰과 컴포넌트 재사용 경계
8. 단위, 컴포넌트, 브라우저와 End-to-End (E2E) 테스트 범위
9. Nginx Open Container Initiative (OCI) 이미지와 배포 Repository 인계 계약

Node.js 버전은 대상 브라우저가 아니라 빌드 도구의 요구 버전과 지원
주기를 기준으로 선택한다. 브라우저 호환성은 빌드 출력 대상, Cascading
Style Sheets (CSS), Web API 사용 범위와 브라우저 검증으로 별도 관리한다.

패키지는 요구사항에서 확인된 필요와 버전, 라이선스, 유지보수성,
브라우저 지원 범위를 확인한 뒤 추가한다. 빌드 도구와 산출물은 배포
방식과 실행 시점 설정 방식을 확인한 뒤 확정한다.

완료 조건은 확정된 선택과 근거가 `docs/implementation.md`에 기록되고, 빈
애플리케이션을 같은 방법으로 재현 가능하게 설치, 검사, 테스트와 빌드할
수 있는 상태다.

## 4. 코드 기반 UI 초안 구현

구현 작업자는 Issue의 인수 조건, 데이터 계약과 화면 상태를 기준으로 React와 CSS
코드를 작성한다. 외부 서비스 계약이 준비되지 않은 상태는 공개 가능한 합성 데이터와
시험 영상으로 재현한다.

초안은 다음 5개 항목을 포함한다.

1. 확정된 데이터와 정보 우선순위
2. 정상, 로딩, 데이터 없음, 오류와 연결 상태
3. 의미 있는 HTML 구조, 레이블, 키보드와 포커스 동작
4. 대상 뷰포트의 기본 배치와 세로 스크롤
5. 인수 조건을 검증하는 데 필요한 테스트 또는 재현 절차

코드와 브라우저 렌더링이 UI 구현의 정본이다. 완료 조건은 사용자가 대상 브라우저에서
검토할 수 있는 실행 가능한 초안과 재현 절차가 준비된 상태다.

## 5. 브라우저 검토와 반복 보정

구현 작업자는 대상 Chrome 뷰포트에서 초안을 렌더링하고 기능 상태를 재현한다. 작업
요청자는 렌더링된 화면을 기준으로 정보 우선순위, 배치, 크기, 색상, 문구와 상호작용을
검토한다. 구현 작업자는 확인된 피드백을 React, CSS, 합성 데이터와 테스트에 반영한다.

검토와 보정은 다음 4단계를 반복한다.

1. 구현 작업자의 대상 상태 렌더링과 검증
2. 작업 요청자의 브라우저 화면 확인
3. Issue에 변경할 결과와 완료 조건 기록
4. 코드 수정과 회귀 검증

완료 조건은 Issue에 정한 정상 및 비정상 상태가 대상 뷰포트에서 확인되고 작업 요청자가
화면 결과를 승인한 상태다.

## 6. 화면 통합과 상태 전이 검증

검토된 컴포넌트를 화면과 경로로 조립한다. 외부 서비스 대신 확정된 계약을
따르는 통제 가능한 합성 데이터와 시험 영상을 사용한다. 시간 흐름, 상태
변경, 재연결, 인증 만료와 설정 변경 충돌을 화면 수준에서 검증한다.

완료 조건은 주요 사용자 흐름을 외부 서비스 없이 재현하고 인수 조건을
확인할 수 있는 상태다.

## 7. 외부 서비스와 사용자 흐름 검증

채택한 브라우저 테스트 도구는 사용자가 보고 조작하는 행동을 기준으로 주요 E2E 흐름을
검증한다. 먼저 통제 가능한 테스트 데이터와 네트워크 응답을 사용해 재현성을 확보한다.
다음으로 통합 환경에서 실제 API (Application Programming Interface), 실시간 갱신,
인증, 실시간 영상과 녹화 영상을 검증한다.

브라우저 테스트는 측정 값 산출 알고리즘의 정확성을 검증하지 않는다. 서버가 제공한
결과와 상태를 브라우저가 계약대로 표시하고 사용자 요청을 전송하는지 검증한다.

완료 조건은 주요 사용자 흐름과 오류 및 복구 경로가 통합 환경에서 확인된 상태다.

## 8. 빌드, 배포 산출물과 운영 검증

로컬에서 재현 가능한 검사, 타입 검사, 테스트와 빌드 명령을 CI에 적용한다. CI 통과 후
프로덕션 빌드를 Nginx OCI 이미지로 패키징하고 같은 image digest를 검증과 배포에 사용한다.

이 Repository의 산출물 검증에는 다음 내용을 포함한다.

- 대상 브라우저의 정적 파일 로드와 기본 경로
- Nginx 컨테이너 시작, 정적 파일 제공과 Single Page Application (SPA) 경로 fallback
- 실행 시점 설정과 자격 증명 분리
- 배포 중 캐시된 Hypertext Markup Language (HTML)와 새 JavaScript 자산의 버전 불일치 방지
- 라이선스 고지, 소스 맵과 보안 정책
- 버전 식별, 무결성 확인과 오류 진단 정보

배포 Repository는 게시된 image digest와 환경별 Nginx 설정을 사용해 Transport Layer
Security (TLS), API와 signaling proxy, 실시간 갱신, 미디어 서비스, 건강 확인과 롤백을
검증한다. Web Real-Time Communication (WebRTC) 미디어는 Nginx를 경유하지 않고
브라우저와 미디어 서비스 사이에서 검증한다.

GitHub Actions 워크플로우는 이미지 빌드, 검사, 게시와 digest 기록 절차가 확정된 뒤
자동화 수단으로 구성한다.

## 역할과 기록 경계

역할과 기록 위치는 5개로 구분한다.

| 역할 또는 도구 | 역할 | 지속 기록 |
| --- | --- | --- |
| 작업 요청자 | 요구사항, 데이터 의미, 화면 피드백과 승인 | 프로젝트 명세와 Issue |
| 구현 작업자 | 계약 확인, 의존성 검토, React 구현, 검증과 문서 갱신 | 코드와 Git 문서 |
| Chrome | 대상 뷰포트 렌더링과 사용자 검토 | 확인 결과를 Issue와 PR에 기록 |
| 합성 데이터와 시험 영상 | 정상 및 비정상 상태의 재현 | 채택한 검증 자산을 코드와 함께 추적 |
| GitHub Actions | 확정된 검증과 배포 절차 자동화 | 워크플로우 파일 |

제품 요구사항과 외부 경계는 `docs/project-spec.md`, 채택한 기술과 구현 결정은
`docs/implementation.md`에 기록한다. 작업 진행 상태와 검토 피드백은 Issue와 PR에
기록한다.

## 현재 출발점

프로젝트 목적과 범위, 현재 모니터링 화면 초안의 설계 참고안, 데스크톱 Chrome과
뷰포트 기준, WebRTC 연결 경계와 OCI 이미지 책임은 준비되어 있다. 인증, 실시간 데이터
형식, 미디어 signaling과 이미지 게시의 세부 계약은 미확정 상태다. Node.js, pnpm, React,
TypeScript, Vite, ESLint, Vitest와 Playwright 기준선은 채택되어 있다. 다음 작업은 현재
모니터링 화면 참고안에서 첫 구현 범위와 인수 조건을 Issue로 승인한 뒤 합성 데이터를
사용하는 화면 골격을 구현하는 것이다.

## 기술 기준 재검토 순서

기술 조사는 다음 10개 순서를 따른다.

1. Repository 책임과 OCI 이미지 인계 경계
2. Node.js 실행 위치, 설치, 버전 고정과 갱신 정책
3. 패키지 관리자, 버전 고정과 lock file 정책
4. React, TypeScript와 빌드 도구 의존성
5. 대상 브라우저, 빌드 출력 호환성과 Web API 정책
6. 공통 스타일, 디자인 토큰과 컴포넌트 재사용 경계
7. 라우팅, 외부 상태, 그래프, 시간, 입력과 미디어 의존성
8. 정적 검사, 단위, 컴포넌트, 브라우저 테스트와 개발 대역 구성
9. 정적 파일, Nginx runtime, 라이선스 고지, 소스 맵과 OCI 이미지
10. 로컬 검증 명령, CI 조건과 Release 절차
